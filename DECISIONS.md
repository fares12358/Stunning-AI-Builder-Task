# DECISIONS.md

Production-improvement exercise for the Stunning AI Builder, as required by `CandidateTask.md`: *"Assume your feature goes to production tomorrow. You have 60 minutes to improve it."*

---

## What did you improve?

I used the available time on the changes with the highest ratio of "breaks the core flow or leaks something sensitive" to "effort," rather than polish:

- **Made persistence failures non-fatal end-to-end.** Saving a chat (`chat.service.js` → `startConversation`/`continueConversation`) is wrapped so a MongoDB write failure never breaks the AI response — the user still gets their answer, they just don't get history for that turn. Chat history is a nice-to-have; the AI response is the product.

- **Found and fixed a real, silent persistence bug.** During targeted debugging, the app looked fine (AI response worked, no errors visible) but `chatId` was `null` on every request, silently disabling follow-ups and Recent Chats. Root-caused it with a direct reproduction script rather than guessing: `mongoose@9.9.3` dropped the legacy `next()` callback for document middleware, so `chat.model.js`'s `pre('validate')` hook was calling `next()` on `undefined` and throwing — an exception that was, correctly but misleadingly, being swallowed by the non-fatal persistence handling above. Fixed the hook to the callback-free signature Mongoose 9 actually expects, then verified live (chat saved, `chatId` returned, follow-up appended to the same conversation, Recent Chats populated). See `TECH.md` for more on this.

- **Hardened the system prompt against generating anything dangerous.** The system prompt (`chat.service.js` → `buildIntegrationsSection`/`buildSystemPrompt`) explicitly instructs the model to never invent API keys, tokens, or credentials for any integration and to reference configuration only via environment variable names. This isn't decorative — it's the one place a careless AI response could otherwise hand a user something that looks like a real secret.

- **Kept the input surface small and validated.** `chat.validation.js` whitelists integration names server-side (never trusts the frontend selector) and caps prompt length; invalid input returns a clean `400` with a specific message instead of a `500` or a silently-wrong request to OpenRouter.

- **Closed the rate-limiting gap this document originally flagged as the biggest production risk.** Added `express-rate-limit` (`backend/src/middleware/rate-limit.middleware.js`) and wired it into both routes that call OpenRouter — `POST /api/chat` and `POST /api/chats/:id/messages` (`chat.routes.js`). It's a per-IP cap of 20 AI requests per 15-minute window, returning a clean `429` with a JSON body once exceeded rather than letting the request through to OpenRouter. Verified live: 20 requests succeed, the 21st and 22nd against the same IP return `429` immediately (no OpenRouter call made). This was a genuine "close it, don't just flag it" fix, not a bolt-on — it directly protects the shared 200-request/day free-tier quota named in `CLAUDE.md`, which is a single global budget every visitor draws from.

- **Tightened CORS.** `app.js` no longer sets `credentials: true` on the `cors()` config. The app has no cookies or sessions (state lives in `localStorage`, confirmed by checking `frontend/src/api/client.js` — no `withCredentials`), so allowing credentialed cross-origin requests had no functional purpose and only widened what a malicious origin could theoretically attempt. Removing it is a no-risk tightening: nothing in the frontend relied on it.

## What did you intentionally leave out?

- **Ownership / visibility scoping on saved chats.** `GET /api/chats`, `GET /api/chats/:id`, and `DELETE /api/chats/:id` have no concept of "whose chat this is" — every visitor sees and can delete every conversation ever saved, because there is no auth and `Authentication / Authorization` is explicitly out of scope per `CLAUDE.md`'s Scope Boundaries. This is a real gap (see "biggest production risk" below) but the correct fix is a session or auth model, which is a scope decision I'm not authorized to make unilaterally here — flagging it clearly is the right call, not quietly working around the boundary with something like a client-generated device ID that would give a false sense of privacy without being a real access control.
- **Raising `max_tokens` above 1500.** Live-testing during the accompanying status report showed a two-integration response getting cut off mid-sentence. I left this alone rather than bump it reflexively, because it's a real cost/latency tradeoff (longer responses = slower + more expensive on a free-tier model with a daily request cap) that deserves a conscious choice, not a default.
- **Automated tests.** Given the ~2-hour scope of the original task, I verified behavior with direct, live API calls (validation edge cases, a real multi-integration build, a follow-up in the same conversation, a zero-integration build, history listing, and now the rate limiter's 429 boundary) instead of writing a test suite. That's a reasonable tradeoff for a prototype of this size, but it's not a substitute for real test coverage before this goes further.
- **A root `.gitignore`.** It currently exists but is empty. `backend/.gitignore` correctly excludes `.env` and `node_modules`, so no secret is actually at risk right now — but there's no repository yet either, so this is a "before you `git init`" item, not a live risk today.
- **Retry/backoff for transient OpenRouter provider errors.** `callOpenRouter` (`chat.service.js`) makes exactly one attempt; any non-2xx response — including a provider-side `429` that has nothing to do with this app's own rate limiting — is surfaced immediately as a `502 "AI service unavailable"`. This isn't hypothetical: I hit it directly while verifying the Docker setup — the configured free-tier model was temporarily rate-limited *upstream* by its provider (confirmed by reproducing the identical `429` with a raw request straight to OpenRouter, no app code involved), and every chat request failed until I switched to a model that wasn't currently saturated. A short retry with backoff (or a provider/model fallback list) would meaningfully improve resilience here, but I didn't add it in this pass — it touches the one function everything else in the chat flow depends on, and a hasty retry policy (no cap, no backoff) can turn a transient hiccup into a self-inflicted denial of service against the shared free-tier quota, which is worse than a single clean `502`.

## What is the biggest production risk?

**No ownership scoping on saved chats — every visitor can read and delete everyone else's conversations.** `GET /api/chats` returns the 20 most recent conversations from *all* visitors with no filtering, and `GET /api/chats/:id` / `DELETE /api/chats/:id` accept any id from any client — there's no session, cookie, or token tying a chat to the person who created it. In practice this means one user's "what I want to build" prompts (which can include business ideas, internal tooling descriptions, or anything else typed into the box) are visible to every other visitor in their sidebar, and any visitor can delete any other visitor's build history. This is worse than the rate-limiting gap I fixed in this pass because it's a standing information-disclosure and data-integrity issue on every request, not something that only bites under abuse.

The reason this is still open rather than fixed: the real fix is a session or auth mechanism, and `CLAUDE.md`'s Scope Boundaries explicitly lists "Authentication / Authorization" and "User accounts or sessions" as things *not* to build for this task. The lowest-risk mitigation available without crossing that boundary would be a random, unguessable client-side identifier (e.g. a UUID minted once and stored in `localStorage`, sent as a header, and used to filter/authorize chat operations) — real privacy still requires actual auth, but it would at least stop casual cross-user enumeration in the sidebar. I did not add even that partial mitigation in this pass because it changes the API contract (`GET /api/chats` semantics, a new required header) and deserves the same conscious sign-off as the rate limiter got, not a silent addition. If there's another pass, this is what I'd do first — and I'd treat it as a design decision to confirm before writing code, since it brushes right up against the auth boundary.
